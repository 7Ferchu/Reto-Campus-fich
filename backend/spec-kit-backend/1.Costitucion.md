# Constitución del Backend CampusFICH

## 1. Propósito

Este documento define las tecnologías, arquitectura, responsabilidades y fases de construcción del backend para el sistema de reservas de las canchas universitarias de CampusFICH.

El backend expondrá una API REST para administrar autenticación, solicitantes, canchas, horarios y reservas.

## 2. Tecnologías oficiales

| Área | Tecnología | Uso |
|---|---|---|
| Lenguaje | TypeScript | Desarrollo del backend con tipado estático |
| Runtime | Node.js | Ejecución de la aplicación |
| Capa HTTP | Hono.js | Creación de la API REST y manejo de rutas |
| Base de datos | PostgreSQL | Persistencia de la información |
| Acceso a datos | Drizzle ORM | Consultas tipadas y migraciones |
| Autenticación | JWT | Identificación de usuarios autenticados |
| Contraseñas | bcrypt | Hash de contraseñas con 8 saltos |
| Validación | Zod | Validación de cuerpos, parámetros y respuestas |
| Pruebas | Vitest | Pruebas unitarias e integración |
| Calidad | ESLint y Prettier | Estándares de código y formato |

## 3. Arquitectura

Se utilizará una arquitectura de **tres capas**, organizada por módulos funcionales. Esta opción combina la separación de responsabilidades del patrón MVC con una estructura escalable para el proyecto.

### 3.1 Capas

#### Capa HTTP

Responsabilidades:

- Definir las rutas de Hono.js.
- Recibir peticiones HTTP.
- Ejecutar validaciones de entrada con Zod.
- Obtener los datos del usuario autenticado.
- Devolver códigos y respuestas HTTP.

Componentes principales:

- Rutas.
- Controladores.
- Middlewares.
- Schemas de entrada y salida.

#### Capa de aplicación

Responsabilidades:

- Implementar los casos de uso.
- Aplicar las reglas de negocio.
- Coordinar repositorios y servicios.
- Validar permisos según el rol del usuario.

Componentes principales:

- Servicios.
- Casos de uso.
- DTOs.
- Errores de dominio.

#### Capa de infraestructura

Responsabilidades:

- Conectarse a PostgreSQL.
- Ejecutar consultas mediante Drizzle ORM.
- Gestionar migraciones.
- Implementar repositorios.
- Proporcionar servicios externos, como JWT y bcrypt.

Componentes principales:

- Esquemas de base de datos.
- Repositorios.
- Configuración.
- Adaptadores.

## 4. Autenticación y autorización

### 4.1 Usuarios y roles

El sistema manejará dos roles principales:

- `administrador`
- `solicitante`

Los solicitantes podrán tener los siguientes tipos:

- `estudiante`
- `docente`
- `administrativo`
- `externo`

### 4.2 Inicio de sesión

El inicio de sesión estará disponible para administradores y solicitantes.

Proceso:

1. Recibir usuario o correo y contraseña.
2. Validar los datos con Zod.
3. Buscar el usuario correspondiente.
4. Comparar la contraseña usando bcrypt.
5. Generar un JWT con el identificador y el rol.
6. Devolver el token sin exponer la contraseña.

### 4.3 Contraseñas

- Las contraseñas nunca se almacenarán en texto plano.
- Se utilizará bcrypt con `8` saltos.
- Las contraseñas no se incluirán en ninguna respuesta de la API.

### 4.4 Cierre de sesión

La primera versión utilizará JWT con expiración definida. El cliente deberá eliminar el token al cerrar sesión.

Para una revocación inmediata de tokens se podrá implementar posteriormente una lista de tokens revocados o refresh tokens.

## 5. Funcionalidades obligatorias

### 5.1 Autenticación

- Iniciar sesión como administrador.
- Iniciar sesión como solicitante.
- Cerrar sesión como administrador o solicitante.

### 5.2 Solicitantes

- Registrar solicitantes.
- Validar el tipo de usuario.
- Validar correos únicos.
- Requerir `CodigoFICH` para estudiantes y docentes.
- Permitir `CodigoFICH` nulo para administrativos y externos.
- Consultar la información propia.

### 5.3 Reservas

- Crear una reserva.
- Consultar las reservas propias.
- Cancelar una reserva propia.
- Validar disponibilidad de cancha y horario.
- Evitar reservas duplicadas para la misma cancha, fecha y horario.

### 5.4 Administración

Solo los administradores podrán:

- Crear, consultar, actualizar y eliminar canchas.
- Crear y gestionar horarios.
- Consultar todas las reservas.
- Confirmar o rechazar reservas.
- Administrar el estado de las canchas y horarios.

## 6. Reglas de negocio

- Los horarios estarán disponibles únicamente de lunes a sábado.
- La hora inicial no podrá ser anterior a las 07:00.
- La hora final no podrá ser posterior a las 22:00.
- La hora inicial deberá ser menor que la hora final.
- Una reserva debe pertenecer a un solicitante y a un horario existente.
- Un solicitante no podrá reservar un bloque ocupado.
- Un solicitante solo podrá consultar y cancelar sus propias reservas.
- Las operaciones administrativas requerirán el rol `administrador`.
- Los estados de reserva serán `confirmada`, `rechazada` y `cancelada`.

## 8. Fases de construcción

### Fase 1: Inicialización

- Crear el proyecto Node.js con TypeScript.
- Configurar Hono.js.
- Configurar `tsconfig.json`.
- Configurar ESLint y Prettier.
- Crear `app.ts` y `server.ts`.
- Crear endpoint de salud `GET /health`.

### Fase 2: Base de datos

- Configurar variables de entorno para PostgreSQL.
- Configurar Drizzle ORM.
- Crear los esquemas de usuarios, canchas, horarios y reservas.
- Crear migraciones.
- Agregar índices para correos, fechas y disponibilidad.
- Agregar una restricción para evitar reservas duplicadas.

### Fase 3: Validación y errores

- Crear schemas Zod por módulo.
- Crear formato estándar de respuestas.
- Crear errores de aplicación.
- Crear middleware global de manejo de errores.
- Validar parámetros, cuerpos y query strings.

### Fase 4: Autenticación

- Implementar registro de solicitantes.
- Implementar hash con bcrypt y 8 saltos.
- Implementar login para ambos tipos de usuario.
- Generar y verificar JWT.
- Crear middleware de autenticación.
- Crear middleware de autorización por rol.
- Implementar logout.

### Fase 5: Solicitantes

- Implementar creación de solicitantes.
- Validar tipos de usuario.
- Validar `CodigoFICH` según el tipo.
- Implementar consulta del perfil propio.
- Proteger información sensible.

### Fase 6: Canchas y horarios

- Implementar consulta pública de canchas y horarios disponibles.
- Implementar CRUD administrativo de canchas.
- Implementar CRUD administrativo de horarios.
- Validar días y horas permitidas.
- Validar relaciones entre canchas y horarios.

### Fase 7: Reservas

- Implementar creación de reservas.
- Validar disponibilidad.
- Implementar consulta de reservas propias.
- Implementar cancelación de reservas.
- Implementar consulta administrativa.
- Implementar confirmación y rechazo administrativo.

### Fase 8: Pruebas

- Crear pruebas unitarias para servicios.
- Crear pruebas de validación con Zod.
- Crear pruebas de autenticación y autorización.
- Crear pruebas de reservas duplicadas.
- Crear pruebas de permisos por rol.
- Crear pruebas de integración de endpoints.

### Fase 9: Documentación y despliegue

- Documentar endpoints y respuestas.
- Crear `.env.example`.
- Crear scripts de migración y carga de datos.
- Configurar Docker opcionalmente.
- Preparar despliegue del backend.
- Revisar logs, seguridad y variables secretas.

## 9. Ajustes requeridos en la base de datos

La base de datos inicial debe ajustarse para soportar todas las funcionalidades:

- Agregar `contrasena` a `solicitantes`.
- Mantener una contraseña almacenada como hash para administradores.
- Agregar el estado `cancelada` a las reservas.
- Agregar una restricción de no duplicidad por cancha, fecha y horario.
- Considerar `fecha_actualizacion` y `activo` en las entidades administrables.
- No devolver las columnas de contraseña en las respuestas de la API.

## 11. Dependencias del backend y compatibilidad con Vercel

### Dependencias de producción

```text
hono              # API HTTP y middleware
zod               # Validación de entradas
jose              # JWT basado en Web APIs
drizzle-orm       # ORM y consultas tipadas
postgres          # Cliente PostgreSQL compatible con serverless
bcrypt            # Hash de contraseñas con 8 saltos
```

### Dependencias de desarrollo

```text
typescript
tsx
drizzle-kit
tsc-alias
@types/node
@types/bcrypt
```

`@hono/node-server` se utilizará únicamente para el servidor local. Vercel importará la aplicación Hono desde `src/app.ts` mediante su exportación `default`.

### Estructura de ejecución

```text
src/app.ts    # Aplicación Hono exportada como default para Vercel
src/local.ts  # Adaptador @hono/node-server para desarrollo local
```

La aplicación se ejecutará en Node.js Runtime porque `bcrypt` utiliza dependencias nativas. No se utilizará Edge Runtime.

Vercel convierte automáticamente las rutas Hono en Vercel Functions. No se iniciará `serve()` dentro de `src/app.ts`, no se ejecutarán migraciones durante un cold start y no se utilizará `serveStatic()`.

La conexión PostgreSQL utilizará `postgres` con `prepare: false` para mejorar la compatibilidad con proveedores serverless como Neon. Las migraciones se ejecutarán desde CI/CD o manualmente antes del despliegue.
